Git 与 GitHub 命令完全指南

一、Git 分支

原始笔记

原始文字还原：

  • git checkout -b feature：创建分支，和主库一模一样，不影响主库，之后可以和主线合并
  • 分支图：已完成的代码在 C1；发现 C1 有 bug 时，创建 C4 分支修复，解决后和 C1 合并；实现新功能时另建分支，最终与主干合并，既修了 bug 又增加了新功能
  • 提交图：Commit #1 → #2 → #3 在主干，#4 → #5 在分出的功能分支上，合并后会包含 feature 与 main 所有的代码

把截图里的命令整理成可复制版本，新版推荐用 switch 代替 checkout 切换分支：

分支的本质是一个指向某次提交的可移动指针，新建分支不会复制文件，因此创建几乎零成本。

二、Pull Request 与代码评审

原始笔记

原始文字还原：

  • Pull Request 用于合并代码，项目管理员可在 PR 页面审核代码，这个过程称为 code review
  • 点击 Review changes 可以决定是否合并，评审有三种结论：
    • Comment：只评论，不决定是否合并
    • Approve：管理员同意，代码可以合并
    • Request changes：要求 PR 发起者对代码做修改
  • 确认无冲突后，点击 Merge pull request 即可，提示 This branch has no conflicts with the base branch 表示可自动合并

PR 不只是合并按钮，更是团队协作中评审、讨论、留痕的载体。完整流程对应到命令行，分支推送与合并如下：

三、仓库的其他功能：Insights

原始笔记

原始文字还原：

  • 仓库 Insights 提供代码统计，Code frequency 统计代码的变动情况（绿色为新增 Additions、红色为删除 Deletions）
  • 还有 Pulse、Contributors、Dependency graph（依赖管理图）、Network、Forks 等

补充

Insights 各面板用途速记：

面板 看什么
Pulse 仓库近期活动概览
Contributors 各贡献者提交量
Code frequency 每周代码增删行数
Dependency graph 项目依赖与依赖安全告警
Network 仓库与 fork 的分支网络

四、Projects 与 Discussions

原始笔记

原始文字还原：

  • Projects：在项目看板里添加和管理待办事项，左下角 Add Item 可新增卡片，分 Todo / In Progress / Done 等状态
  • Discussions：GitHub 的论坛，点击 New discussion 即可发帖，分类含 Announcements、General、Ideas、Polls、Q&A、Show and tell

补充

Projects 适合做轻量看板，Discussions 适合非代码类讨论（问答、想法、公告），与 Issues（具体问题/任务）场景区分使用。

五、GitHub Desktop 基础

原始笔记

原始文字还原：

  • 三个入口：Clone a repository from the Internet（克隆远程库到本地）、Create a New Repository、Add an Existing Repository
  • 克隆下来的项目有一个隐藏的 .git 文件夹，用它来管理版本
  • 在 GitHub 网页点 View all branches → New branch 可建分支；也可在 Desktop 的 Branch 菜单建分支
  • 提交时填写 Summary（必填）和 Description，提交到本地仓库

六、Git 分区概念

原始笔记

原始文字还原：

  • 四个区域：Working Directory（工作区）、Staging/Index（暂存区）、Local Repository（本地仓库）、Remote Repository（远程仓库）
  • 正向流转：git add、git commit、git push；反向：git pull、git fetch、git merge

补充

用一张表理清四个区域与对应命令：

区域 存放内容 进入该区域的命令
工作区 正在编辑的文件 —
暂存区 标记为下次提交的改动 git add
本地仓库 已提交的版本历史 git commit
远程仓库 托管在 GitHub 的历史 git push

git fetch 只把远程更新拉到本地、不改动工作区；git pull = fetch + merge，会直接改动当前分支。

七、Desktop 进阶：放弃修改与暂存

原始笔记

原始文字还原：

  • Discard changes：放弃修改，回退到本地仓库版本，改动文件进回收站
  • Stash all changes：把没写完的代码暂时存起来，之后可 Restore（还原）或 Discard（放弃）
  • 适用场景：代码还没写完，却要对原来的代码操作，可创建新分支，把存储的代码放到新分支，不影响主分支

原始笔记中的处理表：

操作方法 git 命令 效果
commit git add . / git commit -m "msg" 工作区文件提交本地分支
stash git stash 将改动存储起来
discard git reset --hard 抛弃工作区与暂存区的更改
switch git switch <branch_name> 切换分支，本地改动会带到新分支

八、撤回提交：reset / revert / amend

原始笔记

原始文字还原：

  • reset：把本地分支还原到某次提交的状态。若最后一条命令已推到远端，撤回后需要 git push -f，可能弄丢别人的代码，集成分支禁止强推
  • revert：用一个反向操作撤销上一次更改（新增变删除、删除变新增），只做还原，不改变历史
  • amend：修改最近一次提交，若该提交已推到远端，同样需要强推，不建议
  • 原始对比表：
Git 操作 Git 命令 使用场景 注意事项
discard git restore <文件> / git reset --hard 工作区修改还未 commit 舍弃工作区修改
reset git reset <commit ID> 回退到某个 commit，舍弃其后提交 已推送会导致强推，集成分支禁止
revert git revert <commit ID> 用新提交抵消某次 commit 不改历史，适合公共分支
amend git commit --amend 只修改最新一次 commit 已推送会导致强推

补充

reset 三种模式的区别在于改动保留的位置：

凡是会改写历史的操作（reset、amend、rebase），只要对应提交已推送到多人共用分支，就不要使用；公共分支撤销优先用 revert。

十、分支合并策略与 Cherry-pick

原始笔记

原始文字还原：

  • 网页流程：点 Pull requests 选项卡 → New pull request → 把 feature 分支往主干合并 → Create pull request → 审核后 Merge pull request
  • Desktop 三种合并方式：
    • 直接合并（merge）：保留所有提交与 merge 记录，保证可溯源，多人协作向主干合并必须用
    • Squash merge：把多个提交压成一个（如把 C3/C4/C5 合成 C6），历史清爽
    • Rebase：把 feature 分支变基到 main，只有线性记录，必须强推，私有分支可用
  • 原始对比表：
操作 rebase merge squash merge
特点 只有线性提交 保留全部提交与 merge 记录 只出现一条 merge 记录
优点 减少 merge 记录 分支可溯源 历史清爽干净
缺点 必须强推 多一条 merge 记录 细粒度提交被合并
场景 私有分支 多人协作、向主干合并 需要保持记录清爽
  • Cherry-pick：勾选若干提交，把它们单独合并到 main 分支

补充

十一、解决分支合并冲突

原始笔记

原始文字还原：

  • 情况一：内容冲突。feature 和 main 修改了同一文件的同一位置（如 colors.txt 同处分别改成 black/pink），合并时提示冲突，需打开 IDE 手动修改，得到无冲突版本
  • 情况二：pull 时冲突。同事上传的远程代码和本地修改位置相同，拉取时报错，可先把本地修改 stash，拉取后还原，再手动解决
  • 命令行解决：合并报 CONFLICT，手动改文件后 git add + git commit
  • 文件名冲突：两个分支改动了同一文件的文件名，手动删除多余文件，或用 git rm / git add 处理后提交
