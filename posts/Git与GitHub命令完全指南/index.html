远程仓库 Remote Repository 托管在 GitHub 上的仓库，通过 push / pull 同步

六、分支管理

分支是 Git 的核心能力：创建分支时与主库内容一致，在分支上开发不影响主库，完成后再合并。

典型的分支工作流

实际开发中常见这样一条主线：在 main 上拉功能分支开发新特性，同时拉修复分支处理紧急 bug，各自完成后再合并回主干。

七、远程仓库协作

git push -f 会用本地历史覆盖远程。多人共用的主干分支严禁强推；私有分支需要 rebase 整理历史时才使用。

八、暂存改动：stash

当手头代码开发到一半，却需要临时切分支处理紧急任务时，可以用 stash 把未提交的改动先储藏起来，保持工作区干净。

操作 命令 适用场景 注意事项
丢弃工作区改动 git restore <文件> / git reset --hard 修改还未提交，想还原 改动会被直接舍弃
版本回退 git reset <commit-id> 回退到某个提交，舍弃其后的提交 已推送的回退会导致强推，主干禁用

十、标签 tag

标签通常用于标记正式发布的版本，例如 v1.0.0。

十一、分支合并策略

把功能分支合并回主干有三种常见方式，区别在于提交历史的呈现。

合并方式 提交历史 优点 缺点 适用场景
merge 保留全部提交与 merge 记录 分支可溯源，历史完整 多一条 merge 记录 多人协作、向主干合并
squash merge 多条提交压缩成一条 merge 记录 历史清爽干净 细粒度提交被合并 希望主干记录简洁
rebase 只有线性提交，无 merge 记录 历史线性、减少 merge 记录 必须强制推送 私有分支整理历史

十二、Pull Request 与代码评审

Pull Request（PR）是 GitHub 上合并代码的标准流程，也是团队做 Code Review 的载体。

完整流程：

  1. 推送功能分支到远程，进入仓库的 Pull requests 选项卡
  2. 点击 New pull request，选择功能分支合并到主干
  3. 点击 Create pull request，填写标题与说明
  4. 评审人在 Review changes 中给出三种结论之一：
    • Comment：仅评论，不决定是否合并
    • Approve：审核通过，同意合并
    • Request changes：要求发起人修改后再提交
  5. 无冲突时点击 Merge pull request，确认后完成合并

页面提示 This branch has no conflicts with the base branch 表示可以自动合并；若有冲突则需先解决。

13.2 拉取时冲突

git pull 时若本地改动与远程更新冲突，可先把本地改动 stash 储藏，拉取完成后再 stash pop 还原，此时若仍有冲突，按同样方式手动解决。

13.3 文件名冲突

合并中出现文件重命名导致的冲突，可根据实际情况用 git rm 删除多余文件、git add 加入最终保留的文件，再提交完成合并：

十四、Git LFS

普通 Git 不适合推送超过 100 MiB 的大文件。Git LFS（Large File Storage）把大文件内容存放到专用的 LFS 服务器，仓库中只保留一个指针引用。

附：常用命令速查

场景 命令
查看状态 git status
提交全部改动 git add -A && git commit -m "msg"
查看简洁日志 git log --oneline --graph
新建并切换分支 git switch -c <分支名>
储藏临时改动 git stash / git stash pop
安全撤销已推送提交 git revert <commit-id>
首次推送并建立追踪 git push -u origin <分支名>
以 rebase 方式拉取 git pull --rebase
发布版本标签 git tag -a v1.0.0 -m "msg" && git push origin --tags

命令记不住时，优先用 git status 看当前状态、用 git log --oneline --graph 看分支走向，再决定下一步操作，比死记命令更可靠。
